# Форматирование C-кода

## 1. Зачем?

Форматирование не должно быть предметом споров в ревью и не должно
смешиваться с логическими изменениями. Для C/H-файлов проекта выбран
`clang-format`: он распространён, поддерживается LLVM/Clang и умеет
проверять формат без изменения файлов.

`astyle` из Makefile удалён: у него нет режима проверки, который так же
удобно запускать в CI, и он не является стандартным инструментом для
C-проектов вокруг Clang.

## 2. Какие готовые стили есть у clang-format

`clang-format` содержит наборы предустановок (`BasedOnStyle`). Значения
ниже сняты с версии 23.1.3; в других версиях отдельные параметры могут
отличаться.

| Стиль | Отступ | Ширина | Скобки | Указатели | `case` |
|---|---:|---:|---|---|---|
| LLVM | 2 | 80 | `Attach` (`{` на той же строке) | справа: `int *p` | без отступа |
| Google | 2 | 80 | `Attach` | слева: `int* p` | с отступом |
| Chromium | 2 | 80 | `Attach` | слева | с отступом |
| Mozilla | 2 | 80 | `Mozilla` (функции и блоки по-своему) | слева | с отступом |
| WebKit | 4 | без ограничения | `WebKit` | слева | без отступа |
| Microsoft | 4 | 120 | `Custom` | справа | без отступа |
| GNU | 2 | 79 | `GNU` (скобки с новой строки) | справа | без отступа |

Дополнительно у стилей отличается поведение пробелов перед скобками:
например, GNU требует `if (` и `for (`, а LLVM/Google/WebKit по
умолчанию используют `if(` и `for(`.

## 3. Выбранный стиль

За основу взят **LLVM** с переопределениями под текущий код проекта.

Почему LLVM:

- это базовая, наиболее документированная и предсказуемая предустановка;
- она не навязывает жёсткую ширину 80/120 и не имеет специальной
  раскладки скобок, как Mozilla/WebKit/GNU;
- все отличия проекта задаются явно в `.clang-format`, поэтому стиль
  остаётся понятным и воспроизводимым.

Почему не другие:

- **Google/Chromium** — 2 пробела, 80 колонок и отступ у `case`; слишком
  далеко от существующего кода.
- **WebKit** — ближе всего по отступу (4) и отсутствию ограничения
  ширины, но использует свою раскладку скобок и пробелы перед
  управляющими скобками; переопределений было бы не меньше.
- **Microsoft** — 4 пробела, но 120 колонок и указатели справа.
- **Mozilla/GNU** — своя раскладка скобок; GNU дополнительно требует
  `if (` и ширину 79.

## 4. Настройки проекта

Файл `.clang-format` в корне:

| Параметр | Значение | Почему |
|---|---|---|
| `BasedOnStyle` | `LLVM` | нейтральная база, см. выше |
| `IndentWidth` | `4` | так уже написан проект |
| `TabWidth` | `4` | ширина табуляции для отображения |
| `UseTab` | `Never` | в файлах остаются только пробелы |
| `ColumnLimit` | `0` | не ломать длинные строки, макросы и строки конфига |
| `PointerAlignment` | `Left` | принято `char* p`, а не `char *p` |
| `DerivePointerAlignment` | `false` | не угадывать стиль по файлу |
| `SpaceBeforeParens` | `Never` | принято `if(`, `for(`, `while(` |
| `BreakBeforeBraces` | `Attach` | `{` остаётся на строке с `if`/функцией |
| `IndentCaseLabels` | `false` | `case` на уровне `switch` |
| `AllowShortIfStatementsOnASingleLine` | `WithoutElse` | сохранять короткие `if(...) return;` |
| `AllowShortFunctionsOnASingleLine` | `Empty` | не склеивать тела функций |
| `AllowShortLoopsOnASingleLine` | `false` | циклы остаются многострочными |
| `AllowShortCaseLabelsOnASingleLine` | `true` | сохранять `case X: ...; break;` |
| `ReflowComments` | `false` | не переписывать русские комментарии |
| `SortIncludes` | `Never` | порядок include может быть смысловым |
| `AlignTrailingComments` | `false` | не выравнивать хвостовые комментарии |
| `AlignConsecutiveAssignments/Declarations/Macros` | `false` | меньше шума в diff |
| `MaxEmptyLinesToKeep` | `2` | сохранять разделители между секциями |
| `SpaceAfterCStyleCast` | `true` | принято `(char*) malloc`, `(int) value` |

`ColumnLimit: 0` — осознанный компромисс. В проекте есть длинные
`#define`, строки конфига и комментарии; автоматический перенос дал бы
огромный diff и рисковал бы изменить строковые литералы. Если позже
понадобится ограничение, его лучше вводить отдельным решением и
отдельным коммитом.

## 5. Как пользоваться

```sh
make format        # отформатировать main.c, src/**/*.[ch], tests/**/*.[ch]
make format-check  # проверить формат без изменения файлов
```

`make format-check` завершается с ошибкой, если хотя бы один файл
отличается от результата `clang-format`. Эту команду можно добавить в CI.

Форматируются только C/H-файлы. Tcl, Markdown, `.conf` и другие файлы
не трогаются.

## 6. Установка и версия

Проверено на `clang-format 23.1.3`.

Варианты установки:

```sh
# Arch/Manjaro (пакет clang)
sudo pacman -S clang

# Или через pip, если пакета нет
python3 -m pip install --user clang-format
# при ошибке PEP 668:
python3 -m pip install --user --break-system-packages clang-format
```

Проверка:

```sh
clang-format --version
```

Если версия отличается, `make format-check` может показать отличия,
которых не было в версии 23.1.3. В этом случае версию инструмента нужно
согласовать отдельно, а не подгонять код под случайную версию.

## 7. Правила работы

1. Форматирование делается отдельным коммитом, без логических правок.
2. Перед коммитом: `make format` и `make format-check`.
3. После форматирования обязательны `make test` и ручной smoke, если
   менялись файлы приложения.
4. Не нужно вручную выравнивать код «как в соседнем файле»: источник
   истины — `.clang-format`.
5. Если участок нельзя форматировать (например, таблица или макрос с
   важным ручным выравниванием), используйте
   `// clang-format off` / `// clang-format on` и объясните причину в
   комментарии или ревью.
