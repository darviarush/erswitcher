# Методология тестирования

Документ описывает, что и на каком уровне проверяется в erswitcher,
какие проверки уже работают, а какие пока запланированы. Состав тестов
и команды запуска — в [tests.md](tests.md), архитектура — в [arch.md](arch.md).

## Принципы

- Тест проверяет наблюдаемое поведение, а не внутреннюю реализацию.
- Каждый слой проверяется на своём уровне: домен — юнит-тестами,
  порты — через фейки, X11-адаптеры — через мок, окно конфигуратора —
  функциональными тестами.
- Юнит-тесты не зависят от реального `HOME`, дисплея и запущенного
  `erswitcher`; функциональные тесты используют временный `HOME`, а при
  отсутствии `DISPLAY` — виртуальный дисплей.
- Пропущенный тест не считается успешным. Если тест нельзя выполнить,
  это ошибка, а не «зелёный» результат.
- Предупреждения компиляции в тестовой сборке считаются ошибками
  (`-Werror`).
- Покрытие — диагностический показатель, а не самоцель. Покрытие
  тестового кода не входит в оценку.

## Что уже работает

| Проверка | Инструмент | Команда |
|---|---|---|
| Юнит-тесты | Criterion + ASan | `make test-unit` |
| Функциональные тесты | Tcl/Tk и `tcltest` | `make test-functional` |
| Весь набор | обе группы | `make test` |
| ASan/LSan | AddressSanitizer | `make memcheck` |
| Valgrind | Memcheck | `make valgrind VALGRIND_FILTER='commands/*'` |
| Покрытие | gcov + gcovr | `make coverage` |
| Статический анализ | cppcheck и `-fanalyzer` | `make cppcheck` |
| Форматирование | clang-format | `make format-check` |

Фаззинг, имитация нехватки памяти и нагрузочные тесты пока не реализованы.
Это отдельные задачи, а не часть текущего `make test`.

## 1. Юнит-тесты

Каталог `tests/unit/`. Используется Criterion. Собираются два бинарника:

- `tests/unit/test` — приложение и порты. Исходники компилируются прямо
  в тестовый бинарник с ASan; X11 подменяется моком `tests/unit/mock.c`;
- `tests/unit/test-domain` — чистые доменные модули без X11, файлов,
  процессов и системных часов.

Домен (`src/domain/`) не должен использовать X11, файловый ввод-вывод
и wall-clock API. Это позволяет проверять его обычными вызовами функций,
без стенда и без реального рабочего стола.

Юнит-тесты запускаются так:

```sh
make test-unit
```

ASan уже включён в тестовую сборку. Он обнаруживает выход за границы
буфера, use-after-free и утечки памяти. Для полного прогона с явной
проверкой утечек есть отдельная цель:

```sh
make memcheck
```

Если нужно запустить один набор или один тест Criterion, бинарник можно
вызвать напрямую:

```sh
tests/unit/test --filter 'commands/*'
```

## 2. Функциональные тесты

Каталог `tests/functional/`. Проверяется настоящее окно конфигуратора
на Tk: загрузка конфига, подсветка, закладки, сохранение и события X11
через `event generate`.

```sh
make test-functional
```

Tk требует X11. Если `DISPLAY` не задан, `make test-functional` сам
запускает `xvfb-run -a`. Если нет ни дисплея, ни `xvfb-run`, тест
завершается ошибкой.

Функциональные тесты проверяют интерфейс, но не заменяют проверку
главного цикла приложения, трея и реального X11-протокола. Для них
остаются юнит-тесты портов и ручной smoke-тест.

## 3. Динамический анализ

### AddressSanitizer и LeakSanitizer

Тесты приложения и портов собираются с:

```text
-fsanitize=address -g
```

ASan останавливает тест при выходе за границы объекта, обращении к
освобождённой памяти и других типичных ошибках работы с памятью.
LeakSanitizer, как правило, включается вместе с ASan и сообщает об
утечках при завершении процесса.

```sh
make memcheck
```

`make memcheck` запускает полный набор юнит-тестов с ASan и проверкой
утечек. Обычная сборка приложения при этом остаётся без санитайзера.

### Valgrind

Valgrind нужен для подробной диагностики утечек, неинициализированной
памяти и неверных освобождений. Criterion изолирует каждый тест в
отдельном процессе, поэтому полный прогон под Valgrind очень долгий.
Запускается выбранный набор:

```sh
make valgrind VALGRIND_FILTER='commands/*'
```

Для Valgrind собирается отдельный бинарник без ASan: эти инструменты
нельзя совмещать в одном запуске. Успешный результат — `ERROR SUMMARY: 0`
и отсутствие определённых/косвенных утечек.

### Покрытие

Покрытие собирается отдельными объектами с `--coverage`:

```sh
make coverage        # сводка исходников + coverage.html
make coverage-text   # только цветная сводка исходников
make coverage-html   # только HTML по исходникам
make coverage-clean  # удалить артефакты
```

По умолчанию `make coverage` считает только `src/`: тесты и моки
исключены. Показываются две метрики — ветви и строки. Полный отчёт
вместе с тестами можно получить так:

```sh
make coverage COVERAGE_FILTER='.*'
```

Покрытие тестов не используется как критерий качества: ветви
`cr_assert`/`ck_assert` содержат недостижимые при успешном прогоне
ветви обработки ошибок. Ориентироваться нужно на покрытие `src/`.

## 4. Статический анализ и форматирование

Это не тесты, но обязательные проверки перед коммитом:

```sh
make cppcheck
make format-check
```

Приложение также собирается с `-fanalyzer`; предупреждения анализатора
являются ошибками сборки. Статический анализ не заменяет ASan и
Valgrind: он находит только часть проблем, которые проявляются при
выполнении.

## 5. Граничные случаи

### 5.1. Статические буферы

В проекте есть кольцевой буфер ввода `input_buffer_t` с массивами
`word[INPUT_BUFFER_CAPACITY]` и `symbol[INPUT_BUFFER_CAPACITY]`
(`INPUT_BUFFER_CAPACITY == 1024`). При переполнении `input_buffer_push`
начинает запись с начала буфера. Это поведение проверяет тест
`input_buffer_wraps_at_capacity` в `tests/unit/test-domain.c`.

Для статических буферов проверяются три ситуации:

1. заполнение ровно до границы;
2. запись на один элемент больше;
3. запись, значительно превышающая размер.

Ожидаемое поведение должно быть определено заранее: перезапись по
кругу, отбрасывание лишнего или ошибка. ASan ловит именно выход за
пределы массива, но не заменяет проверку логики переполнения.

`input_buffer_t` хранит не строку, а последовательность клавиш и
Unicode-символов, поэтому требование о завершающем `\0` к нему не
применяется. Для строковых буферов (`char[]`) отдельно проверяется
нуль-терминация и корректная обрезка.

### 5.2. Динамическая память

Динамическая память используется в:

- `src/domain/config/config.c` — массивы привязок и compose-правил;
- `src/domain/command-template/command-template.c` — сборка команды;
- `src/infrastructure/x11/clipboard.c` — данные буфера обмена;
- `src/infrastructure/system/config-store-fs.c` — чтение файла;
- `src/infrastructure/system/command-runner-fork.c` — вывод команды.

Утечки и ошибки освобождения ищут ASan/LSan в `make memcheck` и
Valgrind в `make valgrind`. Отдельные «тесты на утечку» обычно не нужны,
но тесты владения всё равно важны: кто освобождает строку, что
происходит при повторной загрузке конфига, отмене команды и замене
содержимого буфера обмена.

Симуляция нехватки памяти (`malloc`/`realloc` вернул `NULL`) пока не
реализована. Если её добавлять, нужен отдельный тестовый бинарник и
подмена через `-Wl,--wrap=malloc`/`--wrap=realloc`. Такой тест не
следует включать в обычный ASan-прогон: перехват аллокатора и ASan
плохо сочетаются. Проверять нужно не только отсутствие падения, но и
корректный код возврата и освобождение уже выделенных ресурсов.

### 5.3. Фаззинг

Фаззинг пока не реализован. Планируемый инструмент — libFuzzer из
Clang. Первый кандидат — разбор UTF-8 в `src/domain/text/text.c`
(`utf8_decode`, `utf8_strlen`): он принимает произвольные байты и
содержит много ветвей проверки корректности.

Фаззер должен работать с буфером, у которого явно выставлен `\0`, а не
передавать сырые байты как C-строку. Пример цели:

```c
#include <stdint.h>
#include <string.h>
#include <wchar.h>

#include "src/domain/text/text.h"

int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    char buf[4097];
    if (size > sizeof buf - 1) return 0;

    memcpy(buf, data, size);
    buf[size] = '\0';

    wint_t out;
    (void) utf8_decode(buf, &out);
    (void) utf8_strlen(buf);
    return 0;
}
```

Сборка и запуск выполняются отдельно от `make test`:

```sh
clang -std=gnu17 -g -fsanitize=fuzzer,address \
    tests/fuzz/utf8.c src/domain/text/text.c -o fuzz-utf8
./fuzz-utf8
```

Фаззинг имеет смысл добавить в CI только после появления стабильной
цели и воспроизводимых настроек. Падение фаззера сохраняется в файл
`crash-*`, который затем используется как регрессионный тест.

### 5.4. Нагрузочные тесты

Отдельного нагрузочного стенда пока нет. Для erswitcher важнее
проверить не пропускную способность, а устойчивость к длинному вводу,
большим конфигам и медленным командам. Эти сценарии частично покрываются
граничными тестами и таймаутами `commands`; отдельная нагрузочная
проверка остаётся в плане.

## 6. Критерии успешного прогона

- `make test` завершается с кодом 0;
- нет пропущенных тестов;
- нет предупреждений компиляции в тестовой сборке;
- ASan/LSan не сообщают об ошибках;
- функциональные тесты действительно выполнились, а не были пропущены
  из-за отсутствия X11;
- тесты не изменили реальный конфиг пользователя.

Сейчас CI запускает `make test` на Linux, macOS и FreeBSD. Покрытие,
Valgrind, cppcheck и фаззинг в CI пока не включены.

## 7. Что проверять при добавлении теста

1. Чистая логика — юнит-тест в `test-domain`.
2. Порт или сценарий приложения — тест с фейковой зависимостью.
3. X11-адаптер — тест через `tests/unit/mock.c`.
4. Окно конфигуратора — функциональный тест в `tests/functional/`.
5. Новый буфер или аллокация — граничный тест и прогон `make memcheck`.
6. Перед коммитом — `make test`, `make cppcheck`, `make format-check`.
