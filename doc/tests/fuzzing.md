# Фаззинг

Практическое руководство по libFuzzer-целям erswitcher. Общая стратегия
и список инвариантов — в [test-metodology.md](test-metodology.md).

## Быстрый старт

Для сборки нужен `clang` с поддержкой libFuzzer. Собрать все фаззеры:

```sh
make fuzz-build
```

Запустить один фаззер на 60 секунд:

```sh
make fuzz FUZZ_TARGET=text FUZZ_SECONDS=60
```

Запустить все цели по 60 секунд каждую:

```sh
make fuzz-all FUZZ_SECONDS=60
```

Удалить бинарники, корпус и артефакты фаззинга:

```sh
make fuzz-clean
```

`make fuzz` сначала собирает все цели, но запускает только выбранную.
`make fuzz-all` запускает цели последовательно. Если одна цель падает,
`fuzz-all` останавливается: следующие цели не запускаются.

Доступные цели:

- `text` — разбор UTF-8;
- `config` — разбор конфига;
- `command` — шаблоны команд;
- `input` — кольцевой буфер ввода;
- `compose` — поиск мнемоник.

## Как читать вывод

Пример:

```text
#8388608 pulse cov: 71 ft: 237 corp: 74/1098b lim: 4096 exec/s: 399457 rss: 559Mb
#24764226 DONE  cov: 71 ft: 237 corp: 74/1091b lim: 4096 exec/s: 405970 rss: 560Mb
```

Основные события:

| Событие | Что означает |
|---|---|
| `INITED` | libFuzzer загрузил корпус и выполнил первый вход. Это старт, а не ошибка |
| `NEW` | найден вход, который покрывает новую ветвь или признак. Вход добавлен в корпус |
| `REDUCE` | вход в корпусе заменён более коротким с тем же покрытием. Это нормальная оптимизация корпуса |
| `pulse` | периодический отчёт о прогрессе. Нового покрытия может не быть |
| `DONE` | прогон завершён по `-max_total_time` или другому лимиту. Это не значит, что ошибок нет: просто за отведённое время падений не найдено |

Поля строки:

| Поле | Значение |
|---|---|
| `cov` | число покрытых счётчиков/рёбер. Это метрика libFuzzer, а не процент gcovr |
| `ft` | число features, включая value-profile и сравнения |
| `corp` | размер корпуса: количество входов и суммарный размер |
| `lim` | текущий максимальный размер входа |
| `exec/s` | скорость выполнения |
| `rss` | потребление памяти процессом |
| `L` | длина последнего входа |
| `MS` | последовательность мутаций, которая привела к текущему входу |
| `DE` | использованная запись словаря |

`NEW`, `REDUCE` и `pulse` не являются ошибками. Рост `rss` сам по себе
тоже не ошибка: libFuzzer накапливает корпус и служебные данные. Ошибкой
считается сообщение санитайзера или ненулевой код выхода.

## Recommended dictionary

В конце нормального прогона libFuzzer может напечатать:

```text
###### Recommended dictionary. ######
"\377\377\377\377" # Uses: 1174625
"\003\000"         # Uses: 1058523
###### End of recommended dictionary. ######
```

Это токены, которые libFuzzer рекомендует добавить в словарь для
будущих запусков. Они найдены через сравнения и value profile. Это не ошибка и
не обязательно патч.

Словарь можно сохранить вручную и передать через `FUZZ_ARGS`:

```sh
make fuzz FUZZ_TARGET=config FUZZ_SECONDS=60 \
    FUZZ_ARGS='-dict=tests/fuzz/config.dict'
```

Для конфига уже есть `tests/fuzz/config.dict`. Не добавляй в него
случайные токены без проверки: словарь должен помогать проходить
синтаксис конфига, а не раздувать корпус.

## Что зависит от FUZZ_SECONDS

`FUZZ_SECONDS` передаётся libFuzzer как `-max_total_time`. Это
**ограничение по времени на одну цель**, а не количество запусков и не
гарантия найти ошибку.

- `FUZZ_SECONDS=10` — быстрый smoke;
- `FUZZ_SECONDS=60` — обычная локальная проверка;
- `FUZZ_SECONDS=600` — длинный ночной прогон;
- `FUZZ_SECONDS=0` — без ограничения по времени, останавливать вручную
  через `Ctrl-C`.

`make fuzz-all FUZZ_SECONDS=60` запускает пять целей последовательно,
поэтому суммарно это примерно пять минут плюс сборка. Фактическое время
может быть чуть больше из-за инициализации и завершения.

## Как понять, что что-то пошло не так

Признаки проблемы:

- команда завершилась с ненулевым кодом;
- в выводе есть `ERROR: libFuzzer`;
- есть `AddressSanitizer`, `LeakSanitizer` или `UndefinedBehaviorSanitizer`;
- есть `runtime error` от UBSan;
- есть `deadly signal`;
- есть строка `Test unit written to ...`;
- в `build/fuzz/artifacts/` появился файл `crash-*`, `leak-*`,
  `timeout-*` или `oom-*`;
- цель не дошла до `DONE`, а процесс завершился.

Если `make fuzz-all` упал, сначала посмотри, на какой цели это произошло.
Из-за `set -e` следующие цели не запускались.

## Что делать при падении

1. Найти артефакт:

```sh
ls -l build/fuzz/artifacts/
```

2. Воспроизвести его на нужном бинарнике:

```sh
build/fuzz/fuzz-config -runs=1 build/fuzz/artifacts/crash-<hash>
```

3. Если падение воспроизводится, исправить код или harness.

4. Добавить вход в регрессионный корпус:

```sh
cp build/fuzz/artifacts/crash-<hash> tests/fuzz/regressions/config/
```

5. Перезапустить цель:

```sh
make fuzz FUZZ_TARGET=config FUZZ_SECONDS=60
```

Makefile копирует `tests/fuzz/regressions/config/` в рабочий корпус,
поэтому регрессия будет проверяться при каждом запуске.

Падение UBSan на длинном порядке в `config_parse_seconds` уже исправлено;
его вход лежит в `tests/fuzz/regressions/config/seed-exponent-overflow`.

## Корпус и артефакты

- `tests/fuzz/corpus/<target>/` — начальные входы, которые хранятся в git;
- `tests/fuzz/regressions/<target>/` — входы, которые раньше вызывали
  падение;
- `build/fuzz/corpus/<target>/` — рабочий корпус, его можно удалить;
- `build/fuzz/artifacts/` — найденные падения;
- `build/fuzz/fuzz-*` — собранные бинарники.

Сгенерированные фаззером входы не попадают в git. Если вход нужно
сохранить как регрессию, положи его в `tests/fuzz/regressions/`.

## Полезные FUZZ_ARGS

```sh
# словарь для конфига
make fuzz FUZZ_TARGET=config FUZZ_SECONDS=60 \
    FUZZ_ARGS='-dict=tests/fuzz/config.dict'

# ограничить максимальный размер входа
make fuzz FUZZ_TARGET=config FUZZ_SECONDS=60 \
    FUZZ_ARGS='-max_len=4096'

# ограничить число выполнений вместо времени
make fuzz FUZZ_TARGET=command FUZZ_SECONDS=0 \
    FUZZ_ARGS='-runs=1000000'

# если отдельный вход зависает
make fuzz FUZZ_TARGET=input FUZZ_SECONDS=60 \
    FUZZ_ARGS='-timeout=10'
```

`FUZZ_ARGS` подставляется перед каталогом корпуса. Параметры libFuzzer
можно комбинировать.

## Проверка перед коммитом

- `make fuzz-build` проходит;
- `make fuzz-all FUZZ_SECONDS=10` завершается с кодом 0;
- в выводе нет санитайзеров и `Test unit written to`;
- новые регрессии добавлены в `tests/fuzz/regressions/`;
- `make test` и `make test-sanitize` проходят.
